## 生效与交付顺序

1. B1–B3 的明确决定已完成。核对本地定稿与已审推荐方案一致，完成批准状态及 V4-F 依赖变更的审查。
2. 在获得 Tracker 写入授权后，以现行任务完整正文为基础应用职责和 AC 差异；新增任务使用真实返回的 Issue ID，回读父子关系与原生依赖。不得从逻辑 ID 猜测 Issue 编号。
3. 保留现行 Accepted、Superseded 与未接受候选的历史身份；对受影响的活动任务先确认现有 writer 已停止，再交接新定义。历史关闭不自动等于新义务验收。
4. 从回读后的完整正式正文形成新的 definition-only 快照，把本文和配套规范纳入 `.dag/definition-index.json`，更新所有选中文件的真实 blob OID。快照保留完整定义，不只保存摘要或链接；不加入 claim、workspace、Agent、运行回执或临时验收状态。
5. 在隔离分支形成候选，验证精确提交的定义索引、图无环、义务覆盖、文档与独立 Standards／Spec 审查。现行集成线只在其既有发布授权和串行集成协议下接受该 Definition Checkpoint；本地修订提交不等于已完成 checkpoint。
6. 生效后按新图执行。先验证来源假设和小型组合案例，再打通筛选 `fast` 的 create／partial／resume／finalize，之后接入 `standard` 候选研究。市场链独立形成完整纵向切片；#97 复验整体分发，#98 只使用最终同候选证据。

- #115 与 Maintainer Decision A 保留。生命周期不得重新扫描调用者对象，也不得把已排除的任意解释器反射攻击重新引入验收。
- A 的独立本地状态由 #108 实现，#69 接入原 create/resume 路由，#97 验证并说明保护条件、同文件系统限制、分发排除及备份/迁移/丢失行为；不新增用户 commitment 参数。#116/#119 的已交付证据与 provider lane 契约不变。
- #108 保留原身份及已有未接受候选作为参考；修订其协议不能将历史候选自动接受，也不因修复次数机械替换任务。
- 原 Spec 的所有未修改义务和最终整体验证仍有效。新增能力或定义差异需取得自己的最终验证证据。

## 本修订的审查标准

- 每项新增生产输入有明确 owner、消费者和独立验收输出；每条 hard edge 对应真实的输出消费。
- 源数据成功、规范化可采纳、完整分母、数学可复算和发布完成分别有证据，互不替代。
- 同日、跨收盘和跨日恢复不会扩大原 cutoff；获取时间仍为真实时间。
- 无日报冒充盘中、板块计数冒充证券去重广度、当前名单反推历史、缺输入自动填值或候选失败改写排名。
- 没有依靠测试替身推断真实来源或真实文件系统可用；没有改变现行发布物或秘密放宽既定门禁。
- 只将已批准分支应用到正式 Tracker；完成回读与 Definition Checkpoint 后才进入执行调度。
